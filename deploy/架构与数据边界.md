# 架构与数据边界

`deploy/README.md` 讲怎么把它跑起来,`deploy/云上安全.md` 讲运维层怎么加固。
**这一份讲的是:什么放哪里、为什么。** 上云前先把这三个判断想清楚。

---

## 一、"本地 vs 上云"这个说法要拆开

它其实是三个不同的问题被混在一起了:

### 1. 生产环境没有"放本地"这个选项

产品要 ICP 备案、要 HTTPS 域名、要 7×24 可用、要能在微信内浏览器打开。
办公室或家里的机器做不到:没有固定 IP、家宽不能备案、断电断网就是事故、被攻击没有防护。

**生产必须整体在云上,这条没得选。**

### 2. 真正的红线是「数据出不出境」

PRD 10.7 要求用户数据存境内。
**最容易把数据送出境的不是服务器,是第三方 API。**

| 组件 | 会送出去什么 | 要求 |
|---|---|---|
| **LLM** ⚠️ | 学生的文书全文、家庭背景、个人陈述;采集到的页面正文 | **必须境内合规模型**。已做成代码约束,见下 |
| 数据库 | 用户全部数据 | 阿里云境内 RDS。**不能用 Neon / Supabase**(在境外) |
| 对象存储 | 护照、身份证、学位证扫描件 | 阿里云 OSS 境内 bucket |
| 短信 | 手机号 | 阿里云短信,天然境内 |

> **这一条已经不靠"记得"了。** `src/lib/llm/region-guard.ts` 会在
> **启动自检**和**每次取 provider 时**双重校验:
> - `anthropic` 直连、`api.openai.com` 等已知境外端点 → **生产环境拒绝启动 / 拒绝调用**
> - 不认识的域名 → 放行但告警,要求人工确认
>
> 为什么用黑名单而不是白名单:白名单会把不认识的合规国内服务商也拦掉,
> 逼得运营去关掉这个检查 —— **一个被关掉的检查等于没有检查**。
>
> 两道都要:后台「AI 设置」页可以把 key 存进数据库**覆盖 .env**,
> 那条路径绕过启动自检,所以运行时还有一道。

## 二、托管 vs 自建:按安全评估

| 组件 | 现状 | 建议 | 安全理由(不是可用性理由) |
|---|---|---|---|
| **PostgreSQL** | ECS 自建 | 🟢 **托管 RDS** | 补丁责任转移;备份落在**另一套存储**上 |
| **文件存储** | 本机磁盘(应用层 AES-256-GCM) | 🟢 **托管 OSS** | 版本控制防勒索/误删;密钥不与密文同机 |
| **OSS / 短信凭据** | `.env` 里的 AccessKey | 🟢 **ECS 实例 RAM 角色** | 磁盘上根本不存 key,见下 |
| **日志** | journald(会滚掉) | 🟡 **SLS** | 机器被拿下 = 证据一起没;等保要求留存 |
| **WAF / DDoS** | 无 | 🟡 **云 WAF** | 应用层限流挡不住 CC;可把 `/admin` 只放行办公 IP |
| **AUTH_SECRET 等** | `.env` 600 | 🔵 KMS(可选) | 收益递减,见下 |
| **Next.js 应用** | ECS + systemd | ⚪ **保持自建** | 容器/K8s 在这个量级只增加攻击面 |
| **Nginx** | 自建 | ⚪ **保持自建** | 同上 |

### 为什么 RDS 的安全价值主要不在"防黑客"

自建 Postgres 的真实风险排序:

1. **忘了打补丁** —— PG 出 CVE 得自己盯
2. **备份和数据同盘** —— `deploy/README.md` 里的 `pg_dump` 就写在本机 `/var/backups`,盘坏了两个一起没
3. **没有审计日志** —— 出事查不到谁动过什么

RDS 直接消掉 1 和 2,3 可选开启(SQL 审计)。
处理护照和身份证,**二级等保大概率跑不掉**,托管服务自带的合规资质能省掉大量测评工作。

### 最大的一个改进:OSS / 短信不该有 AccessKey

现在 `.env` 里装着约 10 个密钥(DB 密码、AUTH_SECRET、CRON_SECRET、OSS AccessKey、
短信 AccessKey、微信私钥路径、LLM key),**全部明文躺在同一台机器的同一个文件里**。

其中 OSS 与短信的 AccessKey 是**长期有效**的 —— 泄露一次就永久有效,除非主动吊销,
而你不会知道它泄露了。

**改用 ECS 实例 RAM 角色**:阿里云把小时级自动轮换的临时凭据注入实例元数据,
应用直接取,`.env` 里这四行可以删掉:

```
OSS_ACCESS_KEY_ID / OSS_ACCESS_KEY_SECRET / SMS_ACCESS_KEY / SMS_ACCESS_SECRET
```

> ⚠️ **这里有个和本项目代码直接相关的坑。**
> 实例 RAM 角色的临时凭据是通过 `100.100.100.200` 元数据接口取的,
> 而 `src/lib/collect/fetch.ts` 的 SSRF 防护**正好把这个地址挡死了**
> (那是必须的 —— 不挡的话,运营被钓鱼粘贴一个链接就能让服务器把云凭据抓回来显示)。
>
> 结论:取凭据必须走**官方 SDK 的实例角色链路**,
> **绝不能**因为要用元数据就放开 SSRF 白名单。这两件事不冲突,但很容易搞混。

### 为什么 `.env` 上 KMS 优先级不高

`src/lib/settings.ts` 里那句注释是诚实的:API key 用 AES-256-GCM 加密存库,
但"同机 `.env` 可解,防的是拖库"。

上 KMS 能防的是"拿到磁盘但没拿到运行时"这个较窄的场景。
在**已经做了实例 RAM 角色**之后,`.env` 里剩下的只有 `AUTH_SECRET`、`CRON_SECRET`、
DB 密码 —— 数量少、可快速轮换。权限 600 + 定期轮换 + 不进 git 已覆盖主要风险。
KMS 留到有余力再说。

---

## 三、托管不等于安全

RDS 配错白名单(`0.0.0.0/0`)、OSS 桶设成"公共读",**比自建还危险** ——
因为你会**以为**它是安全的。

托管转移的是**运维责任**,不是**配置责任**。
`deploy/云上安全.md` 里那份 P0 清单必须逐条过。

---

## 四、本地环境还有什么用

有,而且重要:

- **开发环境** —— 就是现在这套(PGlite + `npm run dev`)
- **数据人工核对** —— 那批院校数据可以在本地库核对完再导上去
- **备份的异地副本** —— 生产备份除了传 OSS,留一份在本地是对的
  (云账号本身出问题时的最后一道)

---

## 五、落地顺序

1. **接 LLM 时选境内模型** —— 已是代码硬约束,但你要知道为什么
2. **RDS + OSS** —— 接真实用户前完成,这是数据丢失和合规的主要风险
3. **ECS 实例 RAM 角色** —— 消掉磁盘上的长期凭据
4. **SLS + WAF** —— 上线第一个月内
5. KMS、等保测评 —— 按业务节奏
